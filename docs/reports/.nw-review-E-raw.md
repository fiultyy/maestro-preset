### E-B03 [阻断] cb-send v3 升格后 msgid 在 HTTP 通道被受理面白名单重组丢弃，"双通道协议不变"承诺不成立
- planRef: L206（cb-send 增 msgid）、L143（P3 验收"cb-send 新旧对拍逐字段一致(新版多 msgid/ver/via/ttl)"）
- evidence:
  - `plugins/host-callback-bridge/http-intake.js:265`: `const line = JSON.stringify({ type: payload.type, from: payload.from, to, body: payload.body })` —— 受理落盘行只重组 4 键，payload 里的 msgid/ver/via/ttl 一律丢弃（validate 也只认 type/from/body/to，`:84-102`）
  - `bin/cb-send:30-31` 现状: `json.dumps({"type":…,"from":…,"to":…,"body": f"[ref:{…}] {…}"})` 4 键；HTTP 通道 POST 原样发 payload（`:47-48`）
  - plan L206: "HTTP 与文件双通道协议不变"
- analysis: cb-send 加 msgid 后：文件桥兜底路径（`cb-send:58` `printf '%s\n' "$payload" >> inbox.log`）落盘行带 msgid；HTTP 优先路径经 /callback 受理后落盘行**不带** msgid。同一命令两条通道产出不同 schema——"双通道协议不变"只在发送侧成立，落盘侧分叉。后果: ①`--msgid` 重发保号在 HTTP 通道失效；②窄腰以 from+msgid 为去重主键（plan L108），HTTP 通道消息没有 msgid → 去重退化或全靠 digest；③P3 验收"逐字段一致(新版多 msgid/…)"若对拍落盘行，HTTP 路径必不符，若只对拍 cb-send 生成的 payload，则掩盖了丢弃。
- suggestion: 方案必须显式裁决: 要么 http-intake 落盘行透传 msgid（改 `:265`，但这动的是"载体一行不动"红线，需在 §0 约束 2 里开显式例外）；要么 cb-send HTTP 通道不发明 v3 字段（v3 只走文件桥）；要么以 HTTP 应答的 `id: randomUUID()`（`http-intake.js:298`）回填作为 msgid 源。并据此修 P3 对拍判据。

### E-B05 [阻断] resolveAddress 优先级 `alias 查 registry > fleet code` 存在同名静默错投，现网已有 alias 歧义实证
- planRef: L62（优先级）、L63（plane 判定）
- evidence:
  - plan L62: "优先级: broadcast(*) > qualified(id@sid) > alias 查 registry > fleet code > 裸旧式兼容路径"
  - 现网 alias 歧义已发生: `~/.dsh/maestro/bridge/dead.log` 实测 `{"reason":"unknown-addressee: alias \"orch1\" is ambiguous across 2 registered consumers; use <alias>@<sessionId>", …}`
  - `orch1` 同时是 fleet code（`bin/session-send:5` "from/to: fleet.json 里的 4 位码(如 orch1/2437)"）
  - 现状两套解析互不知名: `session-send:32-42` `resolve()` 只查 fleet；`plugins/host-callback-bridge/core/addressing.js:59-69` bare 分支只查 registry sessionId/alias。message-bridge 注释原话（`plugins/message-bridge/index.js:36-38`）: "错投比拒收危险"。
- analysis: 若 registry 里某消费者 alias 恰与 fleet code 同名（orch1 是高频名，dead.log 已证明 alias 侧有重名），窄腰 `resolveAddress('orch1')` 按 L62 优先级恒先命中 registry alias，发往 DSH fleet 会话 `orch1` 的消息会被永久劫持到 registry 消费者——静默错投、无死信、无对账痕迹。方案只承诺保留 alias 多持有者的死信措辞，未处理**跨表撞名**（alias vs fleet code）这一更高频冲突。plane 判定（L63）依赖解析结果，错投会连带选错 plane。
- suggestion: 撞名时改为显式死信（复用 "…is ambiguous…" 措辞骨架，reason 注明 alias/fleet 冲突），或规定撞名强制 `agent://` 显式形式；至少在 resolveAddress 返回里带 `ambiguous:true` 让 adapter 拒发。P1 验收"旧式短码解析结果与 session-send resolve() 一致"（L129）应补撞名用例。

### E-B06 [阻断] digestOf 默认 v3 模式对无 msgid 行（cb-send 4 键行/存量 v2）产生恒等摘要——60s 窗内同 from 消息会被误判重而丢弃
- planRef: L72（digestOf 签名）、L75（升级期双查）
- evidence:
  - plan L72: `digestOf(envelope, mode='v3')   // v3: sha256(from\0msgid);v2: sha256(from\0body)`
  - 现网无 msgid 行真实存在且高频: `bin/cb-send:30-31` 4 键 payload；`~/.dsh/maestro/bridge/inbox.log` 尾部实测 `{"type": "ack", "from": "reviewer@nw-plan-review", …}` 等行均无 msgid
  - 现状 digest 实现: `plugins/host-callback-bridge/core/dedup.js:10-19` `material = from === null ? line : \`${from}\u0000${body}\``，签名 `digestOf(line, parsed)`
  - 调用点不传 mode: `file-router.js:353` `const digest = digestOf(line, value)`；`http-intake.js:266` 同
- analysis: 方案把默认参设为 `mode='v3'`（material=from\0msgid），而 file-router/http-intake 现有调用点只传 `(line, parsed)`。对无 msgid 的 v2/4 键行，v3 模式 material 退化为 `from\0undefined`——**同一 from 的所有消息摘要恒等**。叠加"升级期双查: 先 msgid 命中再 digest 命中"（L75）：若 mark 侧用 v3 摘要记窗，60s 内同 from 的第二条不同消息被 seen 命中 → 静默吞消息。方案既没规定 mark 用哪个模式，也没规定无 msgid 行的 digest 退化策略，与 core/dedup.js 现行为（from\0body）也不"逐字兼容"（L72 自称）。
- suggestion: 裁决并写死: digest material 按 `parsed.msgid ?? parsed.body` 分流（有 msgid 用 msgid、无 msgid 用 body），或 digestOf 恒用 from\0body 与现状逐字一致、msgid 只做独立索引；双查写清 seen/mark 两侧各自查/记哪个键。
